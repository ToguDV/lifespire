# ADR-012: i18next + react-i18next internationalization

- **Status:** Accepted
- **Date:** 2026-10-18
- **Related:** [`ARCHITECTURE.md` §16](../../ARCHITECTURE.md), [`docs/api/README.md`](../api/README.md), ADR-011

## Context

The product ships in Spanish now and in English at M6, and the public repository may attract contributors in other languages later. Text embedded in components would make that migration a mechanical rewrite of the whole UI, and dates, numbers and currency need locale-correct formatting.

## Decision

Internationalization uses **i18next + react-i18next** with **one namespace per screen** and **keys in English** (`home.title`). The source locale is `es`, with English scheduled for M6; additional locales are added as new resource files. Dates and numbers use the native **`Intl`** APIs rather than library helpers. **No user-visible text is hardcoded in components.**

## Consequences

- + Translation is a resource-file change, not a code change.
- + English keys keep the code readable while the source content stays Spanish.
- + Native `Intl` avoids an extra dependency and follows the platform's own data.
- − Per-screen namespaces must be registered consistently; a missing key renders as a raw key in production unless tested.
- − Every new screen carries i18n scaffolding from the first commit instead of being retrofitted.
